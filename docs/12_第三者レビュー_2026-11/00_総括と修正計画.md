# 第三者レビュー 総括と修正計画（2026-11-15、仮公開版）

4 つの観点（A: UX と情報設計、B: ビジュアルとブランド、C: 技術・SEO・性能、D: 規約・信頼性・収益化）で、独立したレビュアーがサイト全体を点検した。各報告書は同じフォルダの A〜D。ここでは重複をまとめ、修正の順番と、運営者に決めてもらうことを整理する。指摘番号は各報告書のもの（A の C1〜M3、B-1〜B-21、C-…、D-1〜D-17）。

## 1. 結論

- 土台（静的生成、PR 表記、クレジット、画像の直リンクと無加工、/go/ の中継、探索の URL 復元、自動文がデータだけで作られていること）は公開水準にある。4 者とも「規約との正面衝突は少ない」「骨格はできている」と評価。
- 一方で、公開前に直すべき「重大」が 4 観点合計で 13 件ある。大きな論点は 5 つ。
  1. **売上に直結する導線が弱い。** 作品ページの「FANZAで見る」がスマホで 2 画面下にあり、一覧には出口が無い（A C1、B-3、D-8）。
  2. **画像の見せ方。** 公式の小さい表紙（147×200px）を 1.5〜3.9 倍に引き伸ばしていて、これが「AI 製テンプレ」の最大の原因になっている（B-1）。
  3. **規約上の宿題が 2 つ実装に残っている。** 探索用の公開 JSON が「全件ダンプ」になっている（D-1。自分たちの docs/10 の判定と食い違う）。承認前なのに埋め込み動画の URL に API 用の ID が付いている（D-2）。
  4. **日次の自動更新が、このまま main に入れると初日に止まる。** 全件の再取得が 1 秒 1 件で 60 分の上限を超える（C-1）。本公開の切替（noindex・アフィリエイト・GA4）も人の記憶頼み（C-2）。
  5. **検索に出す前に、薄いページを絞る必要がある。** 作品 1 件だけの出演者ページが全体の 55%（C-3）。
- 運営者の 3 つの要望は、いずれも「賛成、ただし作り方を変える」が 4 者の共通見解。目玉作品は複数化するが自動送りは条件付き、探索の「重み」は廃止してプリセットに、新着の絞り込みは静的なジャンル別ページで。

## 3. 重要（本公開までに直す）

- **トップの 1 画面目**（A I1、B-5、B-11）: ヘッダー直下に入口チップ（探索／新着／セール／ランキング／出演者一覧）。目玉は題名 2 行で高さ半分、比率は画像に合わせる。見出しに大中小を付け、仕組みの説明文（「評価と定番から選んだ作品」など）は消す。
- **新着**（A I2、要望 3）: 期間タブ（今日／7 日／30 日／近日配信）、ジャンル・メーカー・出演者のチップ、日付見出し、ページ送り。D-1 の都合でチップの先は静的なジャンル別一覧ページにする。
- **ランキング**（A I4、B-13）: 評価順と人気順をタブで別 URL、新着順は削除。順位の数字を共通部品に。出演者ランキングは表をやめ、1 行カード（順位・名前・代表作の表紙・作品数と評価）。
- **出演者ページ**（A I5、#27）: 冒頭に最新作と新着 3 件。10 選は上位 3 件を大きく、4〜10 位は 1 行。動画は 1 位のみ。作品数 5 件未満は 10 選を出さない。
- **ラベルと評価の見せ方**（A I6、A I7）: 「新作」は 7 日以内に。「〜追い向け」は事実の言葉に。レビュー 5 件未満の★は「参考」表示、0 件は出さない。
- **検索とパンくず**（A I8、A I9）: スマホは虫眼鏡から全幅の検索欄。探索の結果上部に検索欄。パンくずを全ページ同じ部品に。
- **作品ページの重複と自動文**（A I10、B-6、D-13）: 自動文の「」装飾をやめ、普通の段落に。文末に「作品データから自動で作成」と小さく添える。配信前は「予約受付中（配信日）」。
- **「運営者が選ぶ」の表記**（B-7）: 運営者が指定するまでは「今週の高評価」に。
- **文字と折り返し**（B-8、B-9、B-10）: 文字サイズを 7 段階に。見出し・件数・順位は折り返さない。今日の発見は題名 3 行で省略。
- **コントラスト**（B-12）: 文字用の朱を別トークン（約 5:1）に。2 番手ボタンの枠線を濃く。
- **棚の矢印**（B-14）: PC に左右ボタンと右端のフェード。
- **規約表記の細部**（D-5、D-6、D-12）: 「DMM.com の提供」を「公式の配信元から直接表示」に。掲載停止の期限と手順（3 営業日以内に返信、確認中は非表示、7 日以内に反映）。PR 帯の文言を「本サイトはアフィリエイト広告（PR）を含みます」に。（2026-11-28 対応: 掲載停止の期限と手順を /removal/ に明記。D-5・D-12 は対応済みを確認）
- **計測**（D-7）: 仮公開中から GA4 を入れる。cta_click に位置（top／after_gallery／sticky／modal／hero）。/go/ の gtag 呼び出しは削除。プライバシーポリシーに外部送信先を列挙。
- **年齢確認**（D-10）: 文言を明確に、noscript でも警告、背後を inert、保存は 30 日で失効。（2026-11-28 対応）
- **ボット対策**（D-9）: 申請から承認までは確認画面のしきい値を緩める。
- **X 投稿**（D-11）: 価格を投稿文から外す。生成から 24 時間を超えたカタログでは投稿しない。（2026-11-28 対応）
- **探索ページの性能**（C-4、C-6）: 表示のずれ（CLS 0.83）の原因は、スマホで読み込み後にパネルを閉じる処理。HTML 側で閉じておく。JSON は並列に読み、1 チャンク目で先に描画。項目を番号に置き換えて約 4 割軽くし、既定の並びは直近 90 日分だけ読む。
- **見出しの Web フォント**（C-5）: 1 ページ 30〜37 リクエスト・約 700KB。固定の見出し・ロゴ・数字だけに `text=` で文字を絞って残し（数十 KB）、作品名などの可変文字は端末の明朝に任せる。
- **画像の読み込み**（C-7）: 一覧の先頭 2〜4 枚は lazy を外す。作品ページのサンプル画像は小さい版を並べ、タップで大きい版（最初の 6 枚だけ表示でも可）。
- **.htaccess のリポジトリ管理**（C-8、C-9、重大 5）: 404 を /404.html に、www→apex と http→https の 301、`Options -Indexes`、HSTS・nosniff・Referrer-Policy・X-Frame-Options、`/_astro/` は 1 年キャッシュ、HTML は no-cache、`/data/` は 5 分。deploy.sh の既定 `DEPLOY_KEEP` から `.htaccess` を外す。
- **inode の上限**（C-10）: 今 2.54 万、1 年で 20 万に届く。/go/ の 4,096 ファイルを `.htaccess` の RewriteRule 1 本に置き換える（アフィリエイト ID は .htaccess 側に置ける）。更新日時をフッターから外して全ページの毎日更新を止める。check-dist にファイル数の警告。
- **軸ページ**（C-12、C-13）: 60 件で打ち切らずページ送り。一覧ハブ（重大 5 と同じ）。title と description に作品数・評価・最新配信日を入れる。
- **年齢確認とモーダルの閉じ込め**（C-14、D-10）: 開いている間は背後を `inert` に。（2026-11-28 対応: 年齢確認のみ。探索の作品モーダルは未対応）
- **/go/ の計測**（C-15、D-7）: /go/ 側の gtag 呼び出しを消し、CTA クリック時に beacon で送る。

## 5. 運営者の要望への回答

1. **目玉作品の横スライド。** 複数化は 4 者とも賛成。自動送りは UX 担当が反対、ビジュアル担当が条件付き賛成。共通の条件は「手で送れる（scroll-snap）」「7 秒以上の間隔」「触れたら止まる」「一時停止ボタン」「動きを減らす設定では動かさない」。おすすめは、まず手動のカルーセル（3〜5 件、次の 1 枚を少し見切らせる、PC は矢印）で出し、自動送りは後から足す。作品は運営者が content ID を指定し、無い枠だけ高評価で補う（そのときは「運営者が選ぶ」と書かない）。
2. **探索の「重み」。** 廃止してプリセットに（重大 8）。残すなら「詳細」に格納し、3 段階の言葉で。並び順の根拠を一文で示す（「評価・レビュー数・新しさから当サイトが計算。広告費による順位付けはありません」）。
3. **新着の絞り込み。** 賛成。期間タブ＋チップ＋日付見出し。まずは /new/ のカードにジャンル番号を持たせ、チップで表示を切り替える（探索の JSON は読まない）。検索流入を狙う上位ジャンルだけ `/new/genre/{id}/` の静的ページを作る。作品数 10 件未満の組み合わせは作らない（薄いページを増やさない）。
4. **補足（技術）。** 探索の分かりにくさの一部は待ち時間と表示のずれ（C-4、C-6）。これを先に直すと体感が変わる。

## 7. 決めてほしいこと

1. 公開 JSON の方針: 第一段階（項目の最小化＋Disallow）で進めてよいか。第二段階（PHP の検索 API）まで踏み込むかは、DMM への照会の返事を見てから決める、でよいか。
2. 目玉作品: まず手動のカルーセルで出し、自動送りは後回し、でよいか。
3. 承認前の動画: ID を除いた URL で再生できるか国内で試す（私が URL を用意する）。できなければ承認まで非表示、でよいか。
4. 探索の「重み」は廃止してよいか。
5. 見出しの Web フォント（明朝）: 固定の見出しだけに限定して残す（おすすめ）か、やめて端末の明朝に任せるか。

**案（AI の推奨）**: まず **A（約 1.3 万件）** で本公開し、探索の軽量化（C-6）と /go/ の 1 本化（C-10）が済んだら **B（約 2.1 万件）** に広げる。

- 理由: A は当初の「約 1 万件」に近く、探索 JSON が今の作りでも 4MB 台（圧縮後 1MB 弱）に収まる。inode は約 4 万で上限の 2 割。新作は全件入るので「追う人」に応えられ、古い作品は 20 件以上に絞るので薄い作品ページが増えない。

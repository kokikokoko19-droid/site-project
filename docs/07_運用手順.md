# 07 運用手順

ローカルでの作業手順、GitHub Actions（CI と日次更新）、うまくいかないときの対処をまとめる。設計の根拠は `docs/02_設計方針.md` の 8.1 節（毎日の更新）。決定事項は `docs/00_決定事項.md`、未確認事項は `docs/01_未確認事項.md` が正本で、この文書はそれに従う。

## 1. 前提

- Node.js 22.22 以上と npm（`package.json` の `engines`）。
- 秘密情報（FANZA API ID、アフィリエイト ID、X API キー）は環境変数で扱う。`.env` はコミットしない。
- 作品データは API から実行時に取得したものだけを使う。生成物（`data/catalog.sqlite`、`data/export/`、`public/data/`、`dist/`）はコミットしない（`.gitignore` 済み）。
- `main` には直接コミットしない。ワークフローの変更もブランチを切って PR で入れる。

## 2. ローカルでの手順

### 2.1 準備

```bash
npm ci
cp .env.example .env     # 実データを使うときだけ。.env に値を書く（コミットしない）
```

`.env` の変数:

| 変数 | 用途 | 省略（空欄）したとき |
|---|---|---|
| `FANZA_API_ID` | FANZA API の ID。実データの取り込みに必須 | ingest が終了コード 2 で止まる |
| `FANZA_AFFILIATE_ID` | アフィリエイト ID。実データの取り込みに必須 | 同上 |
| `DB_PATH` | SQLite の置き場所 | `data/catalog.sqlite` |
| `EXPORT_DIR` | JSON の書き出し先 | `data/export` |
| `X_API_KEY` ほか `X_*` | X 投稿用。この手順書の範囲外 | — |

- `EXPORT_DIR` は変えない。`scripts/copy-export.mjs` が `data/export` 固定で読むため、別の場所に出すとビルドが見つけられない。
- `DB_PATH` を空欄以外にしたら、derive と export も `node --env-file=.env --experimental-strip-types src/data/cli.ts derive` のように呼ぶ。`npm run` は `.env` を読まないので、そのままだと ingest と DB がずれる。

### 2.2 合成データで一連を動かす（API 不要）

```bash
npm run ingest -- --synthetic 3000   # 合成データ 3000 件を入れる（API は使わない）
npm run derive                       # ラベル・似た作品・ランキング・今日の候補を計算
npm run export                       # data/export に JSON を書き出す
npm run build                        # prebuild で public/data にコピーしてからビルド（dist/ ができる）
```

- テストは `npm test`。CI と同じ確認をするなら、`--synthetic 500` で上の 4 つを流す。
- 合成データと実データを同じ DB に混ぜない。切り替えるときは `DB_PATH` を分けるか、`data/catalog.sqlite` を消してから始める。

### 2.3 実データで一連を動かす

`npm run ingest` は `.env` を読まない。ingest だけ `node` を直接呼び、`--env-file=.env` を付ける。

```bash
node --env-file=.env --experimental-strip-types src/data/cli.ts ingest --recent-days 7 --refresh --ranked-pages 5
npm run derive
npm run export
npm run build
```

- `--recent-days N`: 直近 N 日の配信開始分を取り込む（既定 7）。
- `--refresh`: 取り込み済みの作品を再取得して更新する。
- `--ranked-pages N`: 人気順の上位 N ページを取り込む。
- `--actress-profiles`: works に出てくる出演者のうち、プロフィール未取得の人だけを取り込む（1回 1500 人まで。`--actress-profiles-max N` で変更）。API は 1 人 1 回、1 秒 1 回なので 1500 人で約 25 分。残りは次回に続く。
- `--actress-profiles-all`: 出演者全員を取り直す（上限は `--actress-profiles-max N` を付けたときだけ）。プロフィールの更新は年に数回で足りる。
- derive と export は API を使わないので、`.env` を渡さなくてよい（2.1 節の `DB_PATH` の注意を除く）。
- 終了コード: 0 成功、1 実行中のエラー（API 側の不調など）、2 使い方・設定の誤り（API ID 未設定を含む）。API ID・アフィリエイト ID の値と URL のクエリは出力されない。

### 2.3.1 初回の36か月取り込み

初回は `--recent-days 1095`（36か月）で、直近3年分の配信開始分を取り込む。

```bash
node --env-file=.env --experimental-strip-types src/data/cli.ts ingest --recent-days 1095 --ranked-pages 5
```

- 窓は件数に応じて自動で分割される。時間がかかるので、途中で止まったら同じコマンドを再実行する（upsert なので重複しない）。
- 取り込み後は `npm run derive` と `npm run export` を実行する。
- 日次は `--recent-days 7 --follow --refresh --ranked-pages 5` に変える（ワークフロー自体の変更は別担当）。

### 2.3.2 指定軸の取り込み

指定した出演者・シリーズ・メーカーの全作品を、期間に関係なく取り込む。

1. `config/follow.json` に id を書く（書き方と id の調べ方は `config/README.md`）。
2. `--follow` を付けて ingest を実行する。

```bash
node --env-file=.env --experimental-strip-types src/data/cli.ts ingest --follow
node --env-file=.env --experimental-strip-types src/data/cli.ts ingest --follow --follow-config path/to/other.json
```

- `--follow-config PATH`: 設定ファイルを変更する（既定 `config/follow.json`）。ファイルがなければ空設定として何もしない。形式が不正なときはエラーで止まる。
- 他のフラグと併用できる。実行順は recent → follow → refresh → ranked。
- 1 id あたり offset の上限（50000）か該当件数の末尾まで取得する。

### 2.4 astro dev で見るとき

`npm run dev`（astro dev）は prebuild を通らない。データを書き出し直したら、そのつど手でコピーする。

```bash
node scripts/copy-export.mjs   # data/export の JSON を public/data にコピーする
npm run dev
```

`npm run build` のときは prebuild が自動で同じコピーを行うので、手で実行する必要はない。

## 3. GitHub Actions

### 3.1 ワークフロー一覧

| ファイル | いつ動くか | 何をするか |
|---|---|---|
| `.github/workflows/ci.yml` | push、pull_request（全ブランチ） | テストと、合成データでのビルド確認 |
| `.github/workflows/daily.yml` | 毎日 日本時間 06:00（UTC 21:00 の前日）、手動 | 日次更新（取り込み → 派生計算 → 書き出し → ビルド） |
| `.github/workflows/smoke.yml` | コミットメッセージに `[smoke]` を含む push（`main` 以外）、手動（`main` にマージしたあと） | 実データの小さな取り込み → ビルドの確認（3.8 節）。配信はしない |

### 3.2 CI（ci.yml）

1. `npm ci`、`npm test`
2. 合成データ 500 件で `ingest` → `derive` → `export`
3. `npm run build`
4. `dist/` を artifact `dist` に 3 日間残す

- 実データ（FANZA API）には触れず、secrets も使わない。どのブランチ・どの PR でも安全に動く。
- タイムアウトは 15 分。同じブランチ（PR なら PR ごと）で新しい実行が始まると、古い実行は取り消される。
- 同じ変更に対して push と pull_request の両方が動く。仕様どおり。
- `dist` は合成データ 500 件で約 17 MB。push と PR で何度も動くと保持分が積み上がるので、ストレージの使用量を見て `retention-days` を縮める。

### 3.3 日次更新（daily.yml）

流れ:

1. checkout、Node 22.22、`npm ci`
2. API 認証情報の有無を判定（`FANZA_API_ID` と `FANZA_AFFILIATE_ID` が両方あるか）
3. 実データのときだけ、DB（`data/catalog.sqlite`）を cache から復元
4. 取り込み
   - 両方ある: `npm run ingest -- --recent-days 7 --refresh --ranked-pages 5 --actress-profiles`（出演者プロフィールは未取得の人だけ、1回 1500 人まで）
   - どちらかが欠けている: `npm run ingest -- --synthetic 3000` で代替。警告とジョブの要約に「合成データで代替」と出す
5. `npm run derive` → `npm run export` → `npm run build`
6. 実データのときだけ、DB を cache に保存
7. `dist/` を artifact `dist` に 7 日間残す
8. 配信（`deploy` ジョブ。実データの実行で、配信用の secrets が揃っているときだけ `dist/` をホストへ転送する。詳しくは 5 章）

環境変数は workflow の `env:` で `DB_PATH=data/catalog.sqlite`、`EXPORT_DIR=data/export` を指定している。

運用上の注意:

- 合成データで代替した実行の `dist` は配信に使わない。合成データのときは DB の cache を復元も保存もしない（合成データが実データの DB に混ざるのを防ぐため）。
- 手動実行: GitHub の Actions タブ → Daily → Run workflow。`recent_days`（既定 7）と `ranked_pages`（既定 5）で取り込み範囲を広げられる。手動実行は `main` で行う（理由は 3.5 節）。
- `schedule` で動くのは `main` ブランチの `daily.yml` だけ。PR の段階では日次で動かないので、最初の動作確認は `main` にマージしたあとの手動実行で行う（3.7 節）。マージ前に実データを確かめるときは `smoke.yml` を使う（3.8 節）。
- 実行は GitHub 側の混雑で数分から十数分遅れることがある。
- public リポジトリでは、60 日間リポジトリに動きがないと schedule が自動停止される。Actions タブで再有効化する。
- タイムアウトは 60 分。日次は同時に 2 つ動かさない（後から来た方が待つ）。
- `dist` の artifact は、サイズ × 保持日数のぶんだけ Actions のストレージを使う。合成データ 3000 件で `dist` は約 90 MB なので、7 日保持で約 630 MB になる。private リポジトリの無料プランは枠が 500 MB なので、超えるときは `retention-days` を縮める。

### 3.4 secrets の登録

GitHub のリポジトリで Settings → Secrets and variables → Actions → New repository secret から、運営者が登録する。

| 名前 | 値 |
|---|---|
| `FANZA_API_ID` | FANZA API の ID |
| `FANZA_AFFILIATE_ID` | アフィリエイト ID |

- 2 つとも登録されるまで、日次は合成データで動く（実データは取り込まれない）。
- 値は Issue、PR、ログ、文書に書かない。入力欄にだけ貼る。
- secrets を渡すのは、認証情報の確認ステップと取り込みステップだけ。`npm ci` などには渡さない。
- X の API キーは日次では使わない（X 投稿の手順は別）。

### 3.5 DB の cache と、7 日で失効する前提の設計

`data/catalog.sqlite` は API からいつでも作り直せる派生物で、正本ではない（正本は API）。cache は作り直しの手間を減らす置き場にすぎない。GitHub の cache は 7 日間アクセスがないと削除される（リポジトリ全体で 10 GB を超えたときも古いものから削除される）。消えても日次が止まらないように、次の作りにしてある。

仕組み:

- 保存のキーは `catalog-db-v1-<run_id>-<試行回数>` で、実行ごとに変える。復元は `catalog-db-v1-` の前方一致で、いちばん新しいものが選ばれる。cache は同じキーで上書きできないので、固定のキーにすると最初に保存した DB が戻り続けて更新されない。そのためキーを毎回変えている。
- 毎日、復元して保存し直すので、通常は期限切れにならない。使われなくなった古い cache は 7 日で消える。
- 保存するのは、取り込みからビルドまでが全部成功した実行だけ。失敗した実行の DB は残さない。
- 保存するのは `data/catalog.sqlite` の 1 ファイルだけ（合成データ 3000 件で約 10 MB）。付随ファイル（`data/*.sqlite-*`）は含めない。合成データでの一連の実行では、終了後に本体だけが残ることを確かめた。
- cache が見つからなくても失敗にしない。空の DB から始める。

cache が失われたとき（日次が 7 日以上止まった、手動で削除した、など）:

- 空の DB から始まり、取り込まれるのは直近 7 日の新着と人気順の上位 5 ページだけ。カタログは前日より小さくなる。実行ログに「cache なし」の警告が出る。
- 範囲を広げて取り直すには、Actions タブ → Daily → Run workflow で `recent_days` と `ranked_pages` を増やして 1 回実行する（例: `recent_days` 90、`ranked_pages` 20）。成功すると、その DB が cache に保存され、翌日以降はそこから続く。API の呼び出し回数と所要時間（上限 60 分）に注意して、様子を見ながら増やす。
- 日次が止まった日数が 7 日を超えるときは、止まった日数より大きい `recent_days` で手動実行する。超えないと、取り込みの窓から漏れた日の新着が入らない。

cache を作り直したいとき（DB が壊れた、スキーマを非互換に変えた）:

- Actions タブ左側の Caches で、`catalog-db-v1-` で始まるものを削除する。
- または `daily.yml` の `catalog-db-v1` を `catalog-db-v2` に上げる。復元の `key`、`restore-keys`、保存の `key` の 3 か所を、そろえて変える。

cache が見える範囲:

- `main` で作った cache は他のブランチからも読めるが、他のブランチで作った cache は `main` から読めない。ブランチで手動実行しても、その DB は `main` の日次に引き継がれない。手動実行は `main` で行う。

### 3.6 失敗したとき

- 通知は GitHub の標準の通知に任せている。メールやチャットへの追加通知は未実装。
- スケジュール実行の失敗通知は、`schedule` の行（cron）を最後に編集した人に届く。GitHub の Settings → Notifications の Actions の項目で、失敗した workflow の通知を有効にしておく。
- 見る場所: Actions タブ → 失敗した実行 → 赤くなったステップのログ。

| 失敗したステップ | 主な原因 | 対処 |
|---|---|---|
| 実データを取り込む（終了コード 2） | 手動実行の入力が整数でない | `recent_days` と `ranked_pages` に 0 以上（`ranked_pages` は 1 以上）の整数を入れて再実行 |
| 実データを取り込む（終了コード 1） | API 側の不調、制限、接続できない | 時間をおいて手動で再実行。毎回接続できないなら 4 章 |
| 派生データ・書き出し・ビルド | 取り込んだデータの形、コードの不具合 | ログを確認。CI（合成データ）も落ちているなら、コードの問題 |
| タイムアウト（60 分） | 取り込み範囲が大きすぎる | `recent_days` と `ranked_pages` を減らして分けて実行 |

### 3.7 初回の動作確認（`main` にマージしたあと）

1. secrets を登録する前に Run workflow を実行する。警告「合成データで代替」が出て、ジョブが成功し、artifact `dist` ができ、`deploy` がスキップされることを確認する。
2. secrets を登録して Run workflow を実行する。実データの取り込みが成功し、「cache なし」の警告が 1 回だけ出ることを確認する。api.dmm.com に接続できないときは 4 章へ。
3. もう一度 Run workflow を実行する。ログに「復元した DB の cache: catalog-db-v1-...」が出て、前回の DB から続くことを確認する。出ないときは、DB の保存と復元ができていない。

### 3.8 `main` にマージする前の実データ確認（smoke.yml）

GitHub の仕様で、`workflow_dispatch`（Run workflow）は既定ブランチ（`main`）にあるワークフローでしか使えない。作業ブランチの段階で実データを確かめるために `smoke.yml` を置いている。

1. secrets（3.4 節）を登録する。
2. コミットメッセージに `[smoke]` を入れて push する（例: `git commit --allow-empty -m "実データ確認 [smoke]"`）。`[smoke]` のない push では何もしない（ジョブがスキップされる）。push のたびに API を呼ばないための印。
3. Actions タブ → Smoke で、取り込み → 派生計算 → 書き出し → ビルドが通ること、ジョブの Summary に「実データ確認（Smoke）の要約」が出ることを確認する。`dist/` は artifact `dist-smoke` に 3 日残る。

- 取り込みは小さい（直近 3 日と人気順 1 ページ、出演者プロフィール）。daily の DB cache には触れず、配信もしない。初回（2026-11-08）は 13 分で、作品 582 件（直近 3 日 497 件＋人気順 100 件）、出演者 748 人。時間の大半は出演者プロフィール（1 人 1 回の呼び出し）。
- 海外 IP（GitHub の runner や検証用コンテナ）からは、API と画像は取れるが、サンプル動画の埋め込み（www.dmm.co.jp/litevideo/…）と商品ページは地域制限・年齢確認のページへ転送される。これらは日本国内のブラウザで確認する（未確認事項 #28・#29）。
- 要約（`scripts/smoke-summary.mjs`）は件数と ID だけを出す。タイトルなどの文字列はログに残さない。項目の埋まり具合（画像・サンプル動画・価格・レビューなど）と URL の形（https かつ dmm のドメイン）を見る。
- `main` にマージしたあとは Run workflow でも動かせる（入力 `recent_days`・`ranked_pages`）。日常の確認は daily の手動実行で足りるので、smoke は「マージ前」「API の挙動が変わったときの切り分け」用。

## 4. api.dmm.com が海外 IP から呼べない場合（未確認事項 #13 参照）

GitHub-hosted runner は、主に米国のデータセンターから動く。api.dmm.com がそこからの接続を拒否する場合（手動実行の取り込みが毎回、接続エラーなどで終了コード 1 になる）の代替は 2 つある。どちらにするかは、未確認事項 #13 の確認結果で決める。

**A. セルフホストランナー（国内の機器にランナーを置く）**

- `daily.yml` の `update` ジョブの `runs-on` を、そのランナーのラベルに変える。ほかの手順はそのまま使える。`ci.yml` は API を使わないので、GitHub-hosted のままにする。
- ランナーの機器に secrets が渡る。private リポジトリで使い、public リポジトリでは使わない（PR 経由で外部の人のコードが動く恐れがある）。
- cache は GitHub の cache サービスを使うので、7 日で失効する性質は変わらない（3.5 節）。

**B. ホスト上の cron（配信先のホストで日次を回す）**

- ホスト側に、このリポジトリのチェックアウトと Node.js 22.22 以上を用意する。
- 秘密情報はホストの `.env` に置く（コミットしない）。
- cron から、2.3 節の 4 つのコマンド（ingest → derive → export → build）を毎日 日本時間 06:00 に実行し、`dist/` を公開ディレクトリに反映する。ホストの時刻が日本時間であることを確認する。
- DB をホストのディスクに置けば cache は要らず、7 日失効の問題もなくなる。`DB_PATH` で場所を決め、バックアップの方法も決める。
- この場合、GitHub Actions の `daily.yml` は取り込みをしない（無効にするか、`schedule` を外す）。失敗の通知はホスト側で別に用意する（cron のメール、終了コードの監視など）。

## 5. 配信（mixhost へ rsync over SSH）

`dist/` を `scripts/deploy.sh` で mixhost（共用レンタルサーバー）へ同期する。接続先は未契約のため、まだ実際の転送はしていない。mixhost 側の画面名・設定値・パスは契約後に確認して埋める（このページでは推測で断定しない）。

### 5.1 しくみ

- 転送は `rsync` over SSH。`--delete` で、`dist/` にないファイルはサーバー側からも消える。ただし `DEPLOY_KEEP`（既定 `.htaccess,.well-known`）に挙げたものは消さず、上書きもしない。
- `daily.yml` の `deploy` ジョブが動く条件は、次の両方。
  1. 実データの実行（`needs.update.outputs.real_data == 'true'`）。合成データの `dist` は本番に出さない。
  2. secrets の `DEPLOY_HOST`・`DEPLOY_USER`・`DEPLOY_PATH`・`DEPLOY_SSH_KEY` がすべて登録済み。1 つでも欠けると、ジョブは「配信を見送り」の通知を出して何も転送せずに終わる。
- ジョブの手順: 判定 → チェックアウト → artifact `dist` のダウンロード → 秘密鍵を `~/.ssh/deploy_key`（権限 600）に書き出し → `ssh-keyscan` で known_hosts を作成 → `scripts/deploy.sh`。鍵はジョブの終わりに（失敗時も）削除する。
- `DEPLOY_CHECK_URL` を登録すると、転送後にその URL の応答を確認し、200 以外ならジョブを失敗にする。

### 5.2 mixhost 側の準備（運営者）

画面名や手順は契約後に確認する。次は「何を用意するか」の一覧で、具体的な操作は mixhost のマニュアルとコントロールパネルで確かめる。

1. SSH を使えるようにする（有効化の方法とポート番号は契約後に確認）。
2. 配信専用の SSH 鍵を作る（手元で）。
   ```
   ssh-keygen -t ed25519 -f ./deploy_key -C "site-deploy" -N ""
   ```
   - 公開鍵（`deploy_key.pub`）をサーバーに登録する（登録場所と方法は契約後に確認）。
   - 秘密鍵（`deploy_key`）は GitHub の secret `DEPLOY_SSH_KEY` に貼る以外に残さない。リポジトリには入れない。
3. 公開ディレクトリのパスを確認する（独自ドメインに対応するドキュメントルート。値は契約後に確認）。これが `DEPLOY_PATH`。
4. 独自ドメインを設定し、公開ディレクトリを向ける（DNS の変更点と反映までの時間は契約後に確認）。HTTPS の有効化も契約後に確認する。
5. 公開ディレクトリ直下の `.htaccess` で `/go/`（中継ページ）に noindex を付ける。`.htaccess` は `DEPLOY_KEEP` で保護されるので、`dist/` に含めずサーバー上に置いてよい。次は例で、`mod_headers` が使えるかは契約後に確認する。
   ```
   <IfModule mod_headers.c>
     <If "%{REQUEST_URI} =~ m#^/go/#">
       Header set X-Robots-Tag "noindex, nofollow"
     </If>
   </IfModule>
   ```
   `<If>` が使えない環境では、`/go/` ディレクトリ内に置く `.htaccess` で `Header set X-Robots-Tag "noindex, nofollow"` を指定する方法もある。ただしその `.htaccess` も `--delete` の対象になるため、`DEPLOY_KEEP` に `go/.htaccess` を足す。

### 5.3 GitHub への secrets の登録（運営者）

3.4 節と同じ場所（Settings → Secrets and variables → Actions → New repository secret）に登録する。値は Issue、PR、ログ、文書に書かない。

| 名前 | 値 | 必須 |
|---|---|---|
| `DEPLOY_HOST` | 接続先のホスト名（契約後に確認） | 必須 |
| `DEPLOY_USER` | SSH のユーザー名（契約後に確認） | 必須 |
| `DEPLOY_PATH` | 公開ディレクトリの絶対パス（契約後に確認） | 必須 |
| `DEPLOY_SSH_KEY` | 秘密鍵の中身（`-----BEGIN` から `END-----` まで全部） | 必須 |
| `DEPLOY_PORT` | SSH のポート。空なら 22 | 任意（mixhost が 22 以外なら必須。契約後に確認） |
| `DEPLOY_CHECK_URL` | 配信後に確認する URL（例: サイトのトップ） | 任意 |

`DEPLOY_KEEP` は既定のままで足りる。変えたいときは、`daily.yml` の「ホストへ配信」ステップの `env:` に足す。

### 5.4 初回の手動配信

自動に任せる前に、手元で 1 回確かめる。

1. 本番用のビルドを用意する（実データ。2.3 節）。`npm run build` で `dist/` を作る。
2. 環境変数を設定する（`.env` は読み込まれないので、シェルで設定する。値は履歴に残らないよう注意する）。
   ```
   export DEPLOY_HOST=...          # 契約後に確認
   export DEPLOY_USER=...
   export DEPLOY_PATH=...
   export DEPLOY_PORT=22           # 契約後に確認
   export DEPLOY_KEY_FILE=./deploy_key
   export DEPLOY_CHECK_URL=...     # 任意
   ```
   変数名は `.env.example` にある。
3. 初回だけ、ホストの公開鍵を known_hosts に入れる（指紋はサーバー側の案内と照合する）。
   ```
   ssh-keyscan -p "$DEPLOY_PORT" -H "$DEPLOY_HOST" >> ~/.ssh/known_hosts
   ```
4. `--dry-run` で転送内容を確認する。何も書き換わらない。
   ```
   scripts/deploy.sh --dry-run
   ```
   確認すること: `deleting` の行に、残したいもの（`.htaccess`、`.well-known`、サーバー上にだけある画像など）が出ていないか。
5. 問題なければ本番へ転送する。
   ```
   scripts/deploy.sh
   ```
6. ブラウザでトップ、探索ページ、`/go/` を開いて確認する。`/go/` のレスポンスヘッダーに `X-Robots-Tag: noindex` が付いているかも見る。
7. 手動で通ったら 5.3 節の secrets を登録する。次回の日次から自動で配信される。急ぐなら Actions タブから Daily を手動実行する（`main` で行う）。

終了コード: 0 成功 / 1 転送または確認 URL の失敗 / 2 設定不足（必須変数がない、`rsync` や `ssh` がない、`dist/` がない、など）。

### 5.5 戻し方・未確認

- 戻し方: 直前の正常な日の `dist` が artifact に 7 日残るので、それをダウンロードして 5.4 節の手順で転送し直す。サーバー側のバックアップ機能の有無は契約後に確認する。
- 未確認（契約後に埋めて、`docs/00_決定事項.md` と `docs/01_未確認事項.md` に反映する）: SSH の有効化の方法、ポート、公開鍵の登録場所、公開ディレクトリのパス、`rsync` が使えるか、`mod_headers` が使えるか、独自ドメインと HTTPS の設定。

## 7. 計測（GA4）とビルド後の検査

設計方針 10 章（イベント）に従う。イベントの送信は `public/analytics/events.js`（全ページで読み込む）、GA4 の読み込みは `src/layouts/Base.astro` の head にある。

### 7.1 GA4 を有効にする

計測は、環境変数 `PUBLIC_GA4_ID` を設定したビルドでだけ有効になる。未設定のビルド（合成データ、CI、`astro dev`）は、gtag.js の読み込みも設定も出さない。`G-` で始まる形式でない値も、未設定と同じに扱う。

1. GA4 でプロパティとウェブのデータストリームを作り、測定 ID（`G-XXXXXXXXXX`）を控える。
2. ビルドする環境に `PUBLIC_GA4_ID` を渡す。
   - ローカル: `.env` に `PUBLIC_GA4_ID=G-XXXXXXXXXX` を書く（`.env` はコミットしない）。Astro が `.env` の `PUBLIC_` 変数を自分で読むので、`npm run build` でそのまま有効になる。
   - GitHub Actions: 本番に配信するビルドのステップの `env:` に `PUBLIC_GA4_ID: ${{ vars.PUBLIC_GA4_ID }}` を足す。測定 ID は HTML に出る公開の値なので、secrets でなく Variables でよい。合成データのビルド（`ci.yml`）には渡さない。ワークフローの変更は、ブランチを切って PR で入れる。
3. ビルドしたら、`dist/index.html` の head に `googletagmanager.com/gtag/js?id=G-…` と `gtag('config', …)` が出ていることを確かめる。

設定はコードで固定している。広告向けの機能は使わない（設計方針 10 章）。

```js
gtag('config', id, { anonymize_ip: true, allow_google_signals: false, allow_ad_personalization_signals: false });
```

### 7.2 送るイベント

| イベント | きっかけ | 主なパラメータ |
|---|---|---|
| `cta_click` | FANZA へのボタン（`[data-cta]`、`/go/` へのリンク全般）のクリック | `content_id`、`cta_type`（work / modal / link） |
| `card_open` | 作品カード（`.card`）のクリック | `content_id`、`place`（explore / modal / list） |
| `sample_play` | サンプル動画の再生ボタン | `content_id` |
| `filter_use` | 探索ページの絞り込み（チップ、選択、チェック、スライダー） | `filter`（chip / select / checkbox / slider）、`filter_key`、`filter_value` |
| `axis_nav` | 作品ページの軸リンク、トップの入口 | `axis`（actress など）、`place`（work / entry） |
| `search` | 検索フォームの送信 | `query_length`、`place`（header / page） |
| `outbound` | `/go/` から公式へ移動する直前（7.5 参照） | `content_id` |

- 検索語、作品名、出演者名、`select` で選んだ値は送らない。検索は文字数だけ、`select` は指定したか解除したかだけを送る。
- リンクや検索の送信で画面が切り替わる操作は `transport_type: 'beacon'` で送る。
- `gtag` が無いとき（未設定のビルド）は、送らずに `window.__events` に `{ name, params }` を積む（最大 200 件）。ブラウザのコンソールで `window.__events` を見れば動作を確かめられる。

### 7.3 GA4 の管理画面でやること

- 集計に使うパラメータ（`content_id`、`cta_type`、`place`、`filter`、`filter_key`、`axis`）をカスタムディメンションに、`query_length` と `filter_value` をカスタム指標に登録する。登録しないとレポートに出ない。
- 探索ページの URL（`/explore/?q=…`）は GA4 に `page_location` として送られ、検索語が残る。拡張計測の「サイト内検索」をオフにし、データの編集（リダクション）の機能で URL のクエリパラメータ `q` を除外する。画面の名前は変わることがあるので、公式ヘルプで確かめる。
- Google シグナルと広告のパーソナライズは、コードで無効にしているのに加え、管理画面でも無効にしておく。
- `src/pages/privacy.astro` の TODO（計測の記述）を、実際の設定に合わせて埋める。公開前に必ず一致させる。

### 7.4 中継ページ `/go/` の `outbound`

`/go/{id}/` は軽量にするため `Base.astro` を使わず、gtag.js も読み込まない。`outbound` を送る 1 行は入れてあるが、`gtag` が無いので今は何も送らない。公式への移動は、作品ページとモーダルの `cta_click`（beacon）で数えられる。`outbound` も使うなら、`/go/` に GA4 のスニペットを足す（移動までの時間が延びる点とのトレードオフ）。

### 7.5 ビルド後の検査（check-dist）

```bash
npm run build                      # postbuild で自動的に検査される
npm run check                      # dist/ ができているときに、検査だけを実行する
node scripts/check-dist.mjs <dir>  # 別のディレクトリを検査する
```

| 検査 | 内容 |
|---|---|
| リンク切れ | HTML の `href` / `src` が `/` で始まる内部リンクの行き先が `dist/` にあるか。`/go/`、`/data/`、`/_astro/`、`/explorer/`、`/analytics/` も含む。外部 URL は対象外 |
| 本文の禁止語 | 本文、`title`、`alt` などに `undefined`、`null`、`NaN`、`[object`、`不明` が出ていないか（テンプレートの値漏れの検出）。スクリプトとスタイルの中は見ない |
| CTA の rel | `/v/` のページの `/go/` へのリンクに `rel="sponsored nofollow"` があるか |
| ページ数の集計 | HTML の件数を、最初の階層ごとに表示する |

- 問題があると、種類ごとに一覧を出して終了コード 1 になる。`postbuild` なので `npm run build` も失敗し、CI と日次更新はそこで止まる（問題のある `dist` を配信しない）。
- 実行時間の目安は 6,000 ページで 1〜2 秒。
- 「不明」は、作品名や定型文に自然に出る語（「行方不明」「ご不明な点」など）だけを `scripts/check-dist.mjs` の `ALLOWED_PHRASES` で除外している。実データで誤検出が出たときは、本当に値漏れでないことを確かめてから、ここに語を足す。
- 6 章の「検査」のうち、リンク切れの確認はこの節で実装済み。画像 404 のサンプル検査と、全ページの「PR」表記の確認は未実装のまま。

## 8. 公開から承認までの手順（アフィリエイトリンクの切替）

承認前のサイトにアフィリエイトリンクを置くことはできない。そのため、公開時はリンクを公式の商品ページ（アフィリエイトIDなし）にし、承認後に切り替える。切替は環境変数 2 つだけで、コードの変更は要らない。実装は `src/lib/links.ts`。

1. **`AFFILIATE_LINKS=off` で公開する。** 未設定でも off になる。「FANZAで見る」は `/go/` 経由で公式の商品ページへ移動する。ページの「PR」表記はそのまま残る。
2. **DMM アフィリエイトの管理画面で「サイトURLを追加申請」する。** 公開済みのサイトの URL を申請し、審査の承認を待つ。
3. **承認後、サイト用ID（例: 末尾 -003）を `FANZA_SITE_AFFILIATE_ID` に設定し、`AFFILIATE_LINKS=on` にして再ビルドする。**
   - on にすると、`/go/` の移動先が API の `affiliateUrl` になる。
   - `FANZA_SITE_AFFILIATE_ID` を設定すると、読み込み時に `affiliateUrl` とサンプル動画 URL のID（`af_id` / `affi_id`）をサイト用IDに差し替える。API 用ID（末尾 -990）のままでよいか、差し替えるべきかは DMM に照会中（docs/01 を参照）。回答が出るまでは `FANZA_SITE_AFFILIATE_ID` を空にしておけば、差し替えは行われない。
4. **GitHub への登録場所。** リポジトリの Settings の Secrets and variables, Actions で登録する。
   - `FANZA_SITE_AFFILIATE_ID`: secrets（Secrets タブ）。
   - `AFFILIATE_LINKS`: variables（Variables タブ）。値は `on` または `off`。
   - ワークフローの build の env に同名で渡すこと（未設定のままだと off のまま）。

## 9. 取り下げ依頼への対応

DMM から特定の作品や出演者の掲載取り下げ依頼が来たとき、または販売終了・非公開の作品のリンクと素材を取り下げるときの手順。

### 9.1 依頼が来たとき（除外リスト）

1. `config/blocklist.json` に該当の ID を追記する。書き方は `config/README.md` を参照。作品は `contentIds`、出演者は `actressIds`（出演者を指定すると、その出演者が出る作品がすべて除外される）。`reason` に依頼の経緯を短く書く。
2. ローカルまたは CI で `npm run export` を実行する。出力（`works.json`、`works-NNN.json`、`meta.json` の rankings・todays、`actresses.json`）から該当作品が外れる。
3. `npm run build` を実行し、`dist` に該当ページが残っていないことを確かめる（`check-dist` が通ること）。
4. 配信する（5 章の手順、または `main` へのマージで `deploy` ジョブ）。
5. 作品の個別ページや特集記事、X の投稿テンプレートに該当作品を手書きで載せていないか（運営者の担当分）を確認し、あれば外す。

- 除外リストは出力から外すだけで、DB の作品データは消さない。依頼が撤回されたら、リストから ID を消して export と build をやり直せば復帰する。
- 除外リストの形式が不正なとき（配列でない、id がない等）は、取り下げの漏れを防ぐため export がエラーで止まる。
- 除外した件数は `npm run export` の出力に表示される（0 件のときは表示されない）。
- 日次更新（`daily.yml`）も同じ export を通るので、除外は毎日の更新でも保たれる。

### 9.2 販売終了・非公開の作品

日次更新の再取得（`refreshExisting`）で API に出なくなった作品は `gone` になり、次の export から自動的に外れる。手作業は不要。ただし依頼で急ぐ場合は 9.1 の手順で先に除外してよい。

### 9.3 offset 上限の変更（2026年12月ごろ）

公式のお知らせにより、API の `offset` の上限が 50,000 から 5,000 に変更される（商品情報API、女優・ジャンル・メーカー・シリーズ・作者検索API）。取り込みは既定で上限 5,000 として動き、期間の窓は取り切れない件数なら日付の中点で分割する。1日の窓でも 5,000 件を超える場合や、指定軸・人気順で上限に達した場合は警告を出して上限までで打ち切る。

- 環境変数 `FANZA_MAX_OFFSET` で上限を変えられる（既定 5000）。変更前の API で旧挙動に戻すときだけ `50000` を指定する。
- 初回の36か月取り込み（2.3.1）は窓が増えて呼び出し数が増える。実行時間とレート制限に注意する。

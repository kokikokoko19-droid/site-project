## 0. 一言でいうと

**「FANZAの作品データを、自分の好みの軸で見て回れるカタログ」**を作る。
文章の量で勝負せず、データの扱い・導線・運用の設計で勝負する。作品ごとの文章は全件自動生成（データ駆動）、サイトの声は運営者が書くハブ記事と特集に集中させる。

参考サイトから採るもの・採らないもの:
- 採る: 8214型の探索UI（重み付け並べ替え、タグ絞り込み、サンプル確認）、hitozuma型の運用（毎日自動更新、X自動投稿、静的生成）。
- 採らない: レビュー引用（規約違反）、動画のmp4直リンク（動作保証外）、画像まとめ記事＋広告バナー（別事業）。

## 1. 読者と利用シーン（仮説）

| シーン | 読者の状態 | サイトが提供するもの | 入口 |
|---|---|---|---|
| 探索 | 時間がある。次に何を見るか決めていない | 軸で見て回る、偶然の発見 | トップ、探索ページ、Xの日次投稿 |
| 追跡 | 特定の女優・シリーズ・メーカーを追っている | その軸の全作品と新着、似た軸 | 検索流入、軸ページ |
| 比較 | セール時など、効率よく選びたい | 絞り込み＋並べ替え、価格と評価の一覧 | セールページ、探索ページ |
| 着地 | Xの投稿から1作品を見に来た | 作品ページで即判断、そこから回遊 | 作品ページ |

未検証。計測で確かめる指標（10章）: 探索操作率、1訪問あたりの作品閲覧数、サンプル再生率、FANZAクリック率。

## 2. 情報設計

### 2.1 ページ種別

| 種別 | URL | 役割 | 文章の出所 |
|---|---|---|---|
| トップ | `/` | 今日の発見（ランダム・新着・セール）、軸の入口、特集とハブ記事 | 運営者のひとこと＋自動 |
| 探索 | `/explore/` | 全対象作品の一覧。絞り込み、重み付け並べ替え、ランダム | 自動 |
| 作品 | `/v/{content_id}/` | データ、サンプル、自動文、ラベル、似た作品、CTA | 自動（A＋B） |
| 女優 | `/actress/{id}/` | 出演作一覧と新着、共演の多い軸 | 自動 |
| シリーズ | `/series/{id}/` | 作品一覧（発売順）、同メーカーの近い軸 | 自動 |
| メーカー | `/maker/{id}/` | 作品一覧、作風ラベルの分布 | 自動 |
| ジャンル | `/genre/{id}/` | 作品一覧、組み合わせの多いジャンル | 自動 |
| 特集 | `/feature/{slug}/` | 運営者が選んだ作品群と、その理由 | 運営者（D） |
| ハブ記事 | `/guide/{slug}/` | 選び方、軸の解説、サイトの使い方 | 運営者（D） |
| ランキング | `/ranking/` | 評価順・人気順・新着順。期間切替 | 自動 |
| 新着 | `/new/` | 直近の配信開始 | 自動 |
| セール | `/sale/` | キャンペーン中の作品 | 自動 |
| 法務 | `/about/` `/terms/` `/privacy/` `/removal/` | 運営者情報、規約、プライバシー、掲載停止窓口 | 雛形をAI、確定は運営者 |

年齢確認はページではなく、初回表示のオーバーレイ（6章）。

### 2.2 導線

- どのページにも「軸への横移動」を置く。作品ページから女優・シリーズ・メーカー・ジャンルへ、軸ページから別の軸へ。
- 「似た作品」は全作品ページに自動で出す（4.4）。
- 特集とハブ記事は、トップと探索ページの上部から常に届く位置に置く。運営者の声がサイトの顔になる。
- 外部へのリンク（FANZA）は、作品ページとカードのモーダルに限定し、必ずPR表記を伴う。

### 2.3 対象作品の範囲（提案）

全作品（数十万件）は対象にしない。初期は次の母集団から約1万件で始め、段階的に広げる。
- 案1: 直近36か月の配信作品のうち、レビュー件数が一定以上のもの。
- 案2: 案1＋運営者が指定する女優・シリーズ・メーカーの全作品。
- 案3: 直近12か月の全作品。

推奨は案2。「追跡」シーンに応えるには指定軸の網羅が要る。閾値は実データを見て決める。

## 3. データモデル

### 3.1 取得元と項目

FANZA API（ItemList, `site=FANZA&service=digital&floor=videoa`）と補助API（ActressSearch, SeriesSearch, MakerSearch, GenreSearch）。項目の詳細は `docs/03`。

| テーブル | 主な項目 |
|---|---|
| works | content_id（主キー）、title、volume_min、released_at、review_count、review_avg、price_min、list_price、deliveries（配信形式と価格）、image_list / image_small / image_large、sample_images（URL配列）、sample_movie（サイズ別URL、pc_flag、sp_flag）、campaigns（title、begin、end）、affiliate_url、fetched_at、status（active / gone） |
| actresses | id、name、ruby、list_url（顔写真URLは保存しない） |
| series / makers / labels / genres | id、name、ruby |
| work_actress / work_genre | 多対多 |
| derived_labels | content_id、label（4.2のルールで毎日再計算） |
| similar | content_id、similar_id、score（4.4） |

### 3.2 保存しないもの（決定）

- 商品紹介文に相当する項目（旧資料の `comment`）は取得しても保存・表示しない。
- ユーザーレビュー本文は取得対象外。件数と平均値のみ使う。
- 女優の顔写真URLは保存しない。
- APIの生応答は保存しない。`request.parameters` にAPI IDとアフィリエイトIDが平文で入るため、必要項目だけ抜いて捨てる。

### 3.3 保持方針（規約確認待ち）

API利用規約のデータ保存・キャッシュ条項を確認するまでは、保守的に次の方針を仮置きする。
- 保存するのはビルドに必要な正規化済み項目のみ。毎日更新し、APIから消えた作品は `gone` にして30日後に削除。
- 画像・動画はダウンロードせず、公式配信URLを参照する（規約で確認済み）。

### 3.4 格納

ビルド時のSQLite 1ファイル（リポジトリには入れない。CIのキャッシュかホスト上に置く）。探索UI用に軽量レコードをJSONに書き出す（4.5）。

## 4. 探索UI

### 4.1 重み付け並べ替え（決定）

5つの軸にスライダーを置き、合成スコアで並べ替える。

| 軸 | 元データ | 正規化 |
|---|---|---|
| 評価 | review_avg と review_count | 件数で補正したベイズ平均（少数レビューの5.0を上に出さない） |
| 新しさ | released_at | 直近ほど高い。指数減衰 |
| 価格 | price_min | 安いほど高い |
| 長さ | volume_min | 好みの長さに近いほど高い（短尺・標準・長尺の3択） |
| 人気 | APIのrank順位 | 順位が上ほど高い |

初期値は「評価0.4、新しさ0.2、価格0.1、長さ0.1、人気0.2」。変更はURLに残し、共有できるようにする。

### 4.2 絞り込み（決定）

ジャンル（AND、上位ジャンルを先に表示）、女優、シリーズ、メーカー、価格帯、収録時間、発売年、セール中、サンプル動画あり、ラベル（5.2）。
絞り込み結果の件数を常に表示し、0件のときは条件を1つ外す提案を出す（空状態の設計）。

### 4.3 カードとモーダル

- カード: パッケージ画像（API `image_small` 以上）、タイトル、女優、収録時間、評価、価格、ラベル最大3つ。
- タップで詳細モーダル: サンプル画像ギャラリー、公式埋め込みの動画（あれば）、自動文、CTA（PR表記付き）、作品ページへのリンク。
- 画像は公式配信URLの直リンク。拡大縮小以外の加工はしない。

### 4.4 似た作品（決定）

ジャンル集合の重なり（Jaccard）を基礎点に、同女優・同シリーズ・同メーカーで加点、発売時期の近さで微加点。上位8件を作品ページに出す。毎日再計算。

### 4.5 実装方式（決定）

- 探索ページはクライアント側で動かす。対象作品の軽量レコード（カードに必要な項目のみ）をJSONで分割配信し、ブラウザで絞り込みと並べ替えを行う。1万件規模なら十分に軽い。
- 作品ページと軸ページは静的HTMLとして事前生成する。
- ランダム表示は、事前生成した「今日の候補」から選ぶ。

### 4.6 検索

タイトル、女優名、シリーズ名、メーカー名の部分一致。静的索引をクライアント側で検索する。全文検索や意味検索は入れない（規模に対して過剰）。

## 5. 自動文（A）とラベル（B）

### 5.1 A: データ駆動テンプレ（決定）

3種類の文を全作品に生成する。すべてAPI項目の組み立てで、描写はしない。ジャンル名はAPIの値をそのまま列挙する。

| 用途 | 長さ | 文型の例 |
|---|---|---|
| 作品ページ | 3〜4文 | `{女優}出演、{メーカー}の{シリーズ}作品。{収録時間}分、{発売日}配信開始。ジャンルは{ジャンル列}。レビューは{評価}点（{件数}件）。` ＋ ラベル由来の1文 |
| カード | 1文 | `{収録時間}分・{評価}点・{価格}円。{ラベル}。` |
| X投稿 | 140字以内 | `{ラベル}。{女優}出演「{題名}」{収録時間}分、{評価}点。 #PR` |

- 文型は各用途に5〜8種類用意し、content_idのハッシュで選ぶ。同じ文の連投を避け、「定型文の羅列」に見せない。
- 項目が欠けるときの規則を全項目に定める（例: 女優なしなら主語をメーカーに、レビュー0件なら評価文を省く）。空欄や「不明」を表示しない。

### 5.2 B: ルールラベル（決定、閾値は仮）

| ラベル | 条件（仮） |
|---|---|
| 新作 | 配信開始から30日以内 |
| 定番 | 配信開始から3年以上、レビュー50件以上 |
| 高評価 | 平均4.5以上、レビュー20件以上 |
| 長尺 | 180分以上 |
| 短尺 | 60分以下 |
| セール中 | キャンペーン期間内 |
| 初見向け | 高評価かつ定番かつ標準尺 |
| シリーズ追い向け | 同シリーズが12作以上（実装の既定値。実データで調整） |
| 出演者追い向け | 同出演者の作品が20本以上（実装の既定値。実データで調整） |
| 作風ラベル | メーカーごとのジャンル分布から機械的に付与（例: 単一ジャンル集中型、幅広型） |

閾値は実データの分布を見て決める。ラベルは絞り込み条件にも使う。

### 5.3 C: 外部LLMの差し込み口（提案）

作品ごとの文章を外部LLMで生成する場合に備え、`works.generated_text` の列と、生成ジョブの差し込み口だけを用意する。使うかどうか、どのモデルか、プロンプトと品質確認は運営者が決める。AI（本リポジトリの作業者）はプロンプトを書かない。

## 6. デザインシステム

### 6.1 方向性（提案）

「落ち着いた専門店」。派手な赤や点滅を使わず、画像が主役になる暗めの背景と、余白で整える。成人向けサイトにありがちな密度の高い配置を避け、カード1枚ごとに呼吸をもたせる。

### 6.2 トークン

- 配色: 背景（濃いグレー2段階）、文字（白〜灰3段階）、強調1色（温かみのある琥珀系）、警告1色。すべてCSS変数で定義し、ライト対応は後回し。
- 文字: 日本語はシステムフォント優先（Hiragino / Noto Sans JP）。見出し・本文・補足の3段階。
- 余白: 8px基準。カードの間隔は16px、セクション間は48px。
- カード: 画像比率はパッケージに合わせて固定。角丸小さめ。影は使わず境界線で区切る。
- 画面幅: スマホ2列、タブレット3列、PC4〜5列。

### 6.3 共通部品

ヘッダー（ロゴ、検索、軸メニュー）、PR帯、カード、ラベル、絞り込みパネル、スライダー、モーダル、ページ送り、フッター（法務リンク、データ更新日時）、空状態、404。

### 6.4 「AIっぽさ」を消すチェック

- 運営者の声が出る場所が、トップ・特集・ハブ記事に必ずある。
- 自動文は文型が複数あり、同じ画面に同じ文型が並ばない。
- データ欠損で空欄や「不明」が表示されない。
- 全ページで部品と余白が揃っている。
- 404、空状態、読み込み中の文言まで書かれている。

## 7. 法務・表示

| 項目 | 方針 |
|---|---|
| 年齢確認 | 初回アクセス時にオーバーレイ。「18歳以上」で入場、「未満」は外部サイトへ。選択は端末に保存。規約上の義務は見当たらないが、業界慣行として設置 |
| PR表記 | ヘッダー直下の帯「本サイトはFANZAアフィリエイトプログラムを利用しており、作品リンクはPRです」、各CTAボタンに「PR」、フッターにも記載 |
| 利用規約・プライバシー | GA4の利用、Cookie、免責を記載 |
| 掲載停止窓口 | `/removal/` にフォーム（Googleフォームか問い合わせフォーム）。対応期限を明記 |
| 運営者情報 | ハンドルネームと連絡先。氏名・住所は非公開（アフィリエイトサイトは特定商取引法の表示義務の対象外）。公開範囲は運営者が決める |
| 画像・動画の権利表記 | 「画像・動画はDMM.comの提供」。APIのクレジット表記は規約確認後に文言を確定 |
| 広告バナー | 置かない。枠だけ空のスロットとして部品に用意（決定事項） |

## 8. 運用設計

### 8.1 毎日の更新（決定）

1. 差分取得: 直近の配信開始分を日付窓で取得、既存作品の価格・セール・レビューを更新、消えた作品を `gone` に。
2. 派生計算: ラベル、似た作品、ランキング、今日の候補。
3. ビルド: 静的HTMLと探索用JSONを生成。
4. デプロイ: ホストへ転送。
5. 検査: リンク切れ、画像404のサンプル検査、ビルド失敗の通知。

実行基盤はGitHub Actionsの日次実行を第一候補。api.dmm.com が海外IPから呼べるかは要確認（呼べない場合はホスト上のcronに切り替える）。

### 8.2 X自動投稿（決定、費用は運営者承認待ち）

- 投稿数: 1日3〜5本。URLなしを基本（1本0.015ドル）、リンクはプロフィール欄と固定投稿に置く。週1回の特集投稿だけURL付き（1本0.20ドル）。
- 文面: 5.1のX用自動文。文型と作品を毎回変え、同一文面の連投を避ける。本文に「PR」を含める。
- 画像: 添付する場合は公式配信の画像を使い、メディア単位で成人向けラベルを付ける。画像のXへの再アップロードがDMM規約と整合するかは要確認。確認まではテキストのみ。
- アカウント: 専用アカウント。センシティブメディア設定を常時オン。プロフィール画像とヘッダーは非成人向け。
- Premium未加入は1日50投稿の上限。計画内に収まる。

### 8.3 監視と通知

ビルド失敗、API取得失敗、X投稿失敗を運営者に通知（メールかSlack）。週1回の数字まとめ（10章）を自動生成。

## 9. 技術スタック（決定）

| 層 | 選定 | 理由 |
|---|---|---|
| サイト生成 | Astro + TypeScript | 静的生成、部分的なクライアント処理（探索UI）を島として載せられる。参考サイトと同系 |
| 探索UI | 軽量なクライアントスクリプト（Preactかvanilla TS） | 1万件規模の絞り込みをブラウザで完結 |
| データ取り込み | Node/TypeScript スクリプト + SQLite | 単純で可搬 |
| CI | GitHub Actions（日次） | リポジトリと同居 |
| ホスト | mixhost か シン・レンタルサーバー（SSHで転送） | 成人向け可を公式に明記。Cloudflare Pagesは書面確認後の候補 |
| ドメイン | Cloudflare Registrar | 成人向けの明示禁止なし |
| 計測 | GA4 + Search Console | 広告向け機能は使わない |

## 10. 計測と検証

### 10.1 イベント（GA4）

探索操作（絞り込み・スライダー）、カード展開、サンプル再生、FANZAクリック（PR）、軸ページ移動、特集・ハブ記事閲覧、X経由の着地。

### 10.2 週次で見る数字

訪問数（検索・X・直接の内訳）、1訪問あたりの作品閲覧数、探索操作率、サンプル再生率、FANZAクリック率、成約数と報酬（FANZA管理画面から手入力）、X投稿数と費用。

### 10.3 仮説の判定

- 需要仮説: 探索操作率と1訪問あたり閲覧数が、着地だけの訪問より高いか。
- 差別化仮説: 探索ページ経由のFANZAクリック率が、作品ページ直行より高いか。
- 集客仮説: X経由と検索経由の訪問数の推移。90日時点での到達点を既存の90日検証計画と突き合わせる（資料共有待ち）。

## 11. 段階3（基盤）の作業分割

1. データ取り込み: APIクライアント、正規化、SQLite、差分更新。合成データでのテスト。
2. 派生計算: ラベル、似た作品、ランキング、今日の候補。
3. サイト生成: ページ種別ごとのテンプレート、デザインシステム、探索UI。
4. 法務ページと年齢確認、PR表記。
5. CIと配信、監視。
6. X投稿ジョブ（プラン承認後）。

実装はOpus／Sonnetが担当し、設計判断とレビューはFableが行う。合成データは露骨な語を含まないものを用意し、実データでの確認は運営者環境で行う。

## 12. 運営者に決めてほしいこと（この文書のレビュー項目）

1. 対象作品の範囲（2.3の案1〜3）。
2. デザインの方向性（6.1）。参考にしたいサイトがあれば教えてほしい。
3. X投稿の本数と費用の上限（8.2）。
4. 運営者情報の公開範囲（7章）。
5. ホストの選定（9章）。
6. 外部LLMの差し込み口を今の段階で用意するか（5.3）。
